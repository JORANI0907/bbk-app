### 분석은 누가 하나
- **3D 모형 제작** = Claude Code(대화 세션). 자료함의 도면·대장·참고사진을 읽고 Blender 로 모형을 만들어 주소를 등록한다. 호점당 1회성, 사람 판단이 필요한 일.
- **구역·품목 초안 자동 추출** = Claude API(앱 안 자동, 미구현). 도면을 올리면 즉시 초안이 나오는 방식. 건당 비용 수백 원 수준. 잠재고객 제안 흐름에 맞으면 다음 단계에서 구현.

### AI 초안 추출 — 하네스 설계 (4-Layer)

| Layer | 내용 | 위치 |
|---|---|---|
| 1 Input | 시스템 프롬프트 ROLE/TASK/FORMAT/CONSTRAINTS 4섹션, 자료 블록(PDF·이미지) 앞 · 지시문 뒤, 기존 구역 이름 전달 | `src/lib/ai/care-manual-draft/prompt.ts` |
| 2 Execution | `claude-opus-5-5`, 구조화 출력(JSON 스키마), effort medium, 요청 타임아웃 4분, **시도 최대 2회**(불합격 시 문제점을 붙여 재요청), 거절·토큰 초과 처리 | `src/app/api/admin/customers/[id]/care-manual/ai-draft/route.ts` |
| 3 Evaluation | Rubric 100점 · 합격 70. 테스트셋 정상·경계·실패 3종 | `src/lib/ai/care-manual-draft/validate.ts`, `src/lib/__tests__/care-manual-draft.test.ts` |
| 4 Feedback | 불합격·오류는 서버 로그 `[ai-draft][L1~L5]`. 관리자는 초안을 보고 구역 단위로 골라 추가(자동 저장 없음) | 운영 후 실패 사례 DB 로 승격 예정 |

Rubric (`scoreDraft`):

| 항목 | 만점 | 기준 |
|---|---|---|
| zones | 20 | 구역 1~20개 (0개·초과 → 0점, 즉시 불합격) |
| coverage | 20 | 품목이 1개 이상인 구역 비율 |
| titles | 20 | 제목 있고 구역 안 중복 없는 품목 비율 |
| detail | 20 | 설명 10자 이상 품목 비율 |
| frequency | 10 | 빈도가 정해진 품목 비율 |
| safety | 10 | 개인정보·"정기케어"·금액 표현 없음 (하나라도 있으면 0) |

비용: 도면 PDF 1~3장 기준 건당 약 300~800원 (입력 10만 토큰 · 출력 5천 토큰 ≈ 700원). 화면에 "약 N원"으로 표시.

### 구역 사진: 평면이 기본, 360 은 선택 (2026-11-08 결정)
- 사용자 결정: 360 카메라 대신 **휴대폰 평면 사진**을 기본으로. 이유 — 위치 감각은 도면 기반 3D·평면도가 맡게 됐고, 직원이 현장에서 바로 올릴 수 있어야 사진이 꾸준히 갱신됨. 카메라 구매 보류.
- 구현: `PanoramaV2.kind = 'flat' | '360'`(없으면 360, 호환). 올릴 때 2:1 비율이면 자동 360. 평면 표시는 사진 비율 좌표 `x·y`(점) / `points[x,y]`(영역), 뷰어 `FlatPhotoViewer.tsx`(확대·끌기·표시). 360 기능은 그대로 유지.
- **품목 사진 가져오기**: 품목에 이미 올라간 사진을 구역 사진으로 끌어와(`source_item_id`, 파일 복사 없음) 표시를 찍을 수 있음. 삭제해도 품목 쪽 파일은 지우지 않음.
- 용어: "360 사진" → **"구역 사진"**. 구조: 건물 › 층 › 구역 › (작업 묶음 › 품목) / (구역 사진 › 표시).

### 도면·자료가 없을 때 (2026-11-08 추가)
1. **손그림 사진** → 도면으로 올려 분석 (코드 변경 없음)
2. **글로 설명하기** → 도면 분석 창의 모드 전환. `ai-layout` 에 `description` 전달, 같은 스키마·채점·미리보기
3. **평면 그리기·수정** (`FloorPlanEditor.tsx`, `plan-edit-utils.ts`) — 층 추가, 네모 끌어 그리기, 이동, 모서리 크기 조절(네모)·꼭짓점 이동(다각형), 이름·종류·구역 연결(새 구역 만들기 포함), 도면 사진 밑그림. AI 결과도 여기서 고친다. 즉시 3D·평면도 반영, 저장은 [저장].

## 1. 한 줄 목표

고객과 직원 모두가 **"우리 공간이 어디까지, 어떻게 관리되고 있는지"를 3D 모형 → 360 사진 → 품목 메뉴얼 순서로 30초 안에 확인**할 수 있게 한다.
같은 화면을 잠재 고객에게 "케어 범위 지도"로 보여주는 영업 자료로도 쓴다.

중점 3가지: **가시성** (한눈에) · **조작 편의** (휴대폰에서 손가락 하나로) · **정보 전달** (사진 위 표시 → 품목 설명까지 끊김 없이)

## 3. 추천 방향 (대표님 의도 + 내 검토 의견)

### 3-1. 3D는 "실사 복원"이 아니라 "깔끔한 모형"으로 — 핵심 추천

대표님 의도대로 3D를 만들되, 사진을 이어붙여 실사처럼 복원하는 방식(사진 스캔, 포토그래메트리)은 **권하지 않습니다.**

| | 실사 스캔 3D (Polycam·Luma 등) | 깔끔한 모형 3D (추천) |
|---|---|---|
| 사무실·매장 내부 품질 | 유리·흰 벽·반사면에서 구멍·일그러짐 많음 | 도면 기준이라 항상 반듯함 |
| 휴대폰에서 속도 | 파일 50~300MB, 저사양 폰 멈춤 | 1~3MB, 어디서든 부드러움 |
| 수정 (가구 바뀜, 구역 추가) | 재촬영·재생성 | 모형 파일만 수정 |
| 브랜드 느낌 | 어수선함 | BBK 색상·구역 색이 그대로 입혀짐 |
| 제작 시간 (호점당) | 촬영 반나절 + 생성 수시간, 실패 잦음 | 도면 있으면 반나절~1일 |

**실사감은 360 사진이 맡고, 3D는 "어디가 어디인지" 안내판 역할**을 하는 게 가시성·조작편의 두 가지에 모두 맞습니다. 고층 건물이면 층을 쌓아 올린 모형에서 층을 선택해 들어가는 방식(도면 분해 보기)이 특히 잘 어울립니다.

### 3-2. 전체 구조 (고객 눈에 보이는 순서)

```
[탭: 공간 보기]                 [탭: 메뉴얼 목록] (기존)
 ┌──────────────────────┐
 │  3D 모형 (손가락으로 돌림) │  층 선택 ▣ 5F ▣ 6F ▣ 7F
 │  구역별 색상 = 기존 구역 색 │  구역 위 점 색 = 관리 상태
 │  구역 클릭 ↓             │
 ├──────────────────────┤
 │  360 사진 (드래그로 둘러봄) │  구역 안 여러 지점 이동
 │  사진 위 표시(점·영역)    │  초록=정상 / 노랑=주의 / 빨강=조치필요
 │  표시 클릭 → 코멘트 말풍선 │  "후드 필터 · 주 1회 · 지난 점검 11/5"
 │  [메뉴얼에서 보기] 버튼 ↓  │
 └──────────────────────┘
        → 메뉴얼 목록 탭의 해당 품목으로 자동 스크롤 + 강조
```

### 3-3. "관리가 잘되고 있는지 체크" — 상태 색상 연동 (추가 제안)

코멘트 표시의 **색상을 직원 점검 기록과 자동 연결**하면 고객 신뢰 효과가 가장 큽니다.

- 직원이 현장에서 품목 옆 체크(완료 / 특이사항) → 저장
- 360 사진 위 그 품목 표시가 초록으로 바뀌고 "마지막 점검 11/5" 표시
- 빈도(주 1회 등) 대비 점검이 늦어지면 노랑, 특이사항이 있으면 빨강
- 고객은 사진만 봐도 "지금 어디가 잘 되고 있고 어디를 봐야 하는지" 파악

→ 직원 입장에서도 체크 한 번으로 고객 보고가 끝나므로 양쪽 모두 편해집니다.

### 3-4. 기성 서비스(Matterport)와 직접 구축 비교

| | Matterport (스캔 + 태그 서비스) | 직접 구축 (추천) |
|---|---|---|
| 첫 결과물까지 | 1~2주 (가장 빠름) | 3주 (360+표시) / 7주 (3D까지) |

## 5. 데이터 구조 변경 (기존 v2 확장, 깨지지 않게)

기존 `care_manual` JSON은 그대로 두고 필드만 추가합니다. 없으면 지금과 똑같이 동작합니다.

```
customers.care_manual (v2 그대로)
  zones[]
    + space: { model_zone_key }          ← 3D 모형 안 구역 이름과 연결
    + panoramas[]                         ← 구역당 360 사진 여러 장
        { id, image_url, thumb_url, title, links[] (다른 지점으로 이동) }
        markers[]                         ← 사진 위 표시
          { id, item_id, type: 점|영역, position, label, note }
    groups[].items[]  (변경 없음 — item_id 로 마커가 가리킴)

새 테이블 care_manual_checks            ← 직원 점검 기록
  customer_id, item_id, checked_at, worker_id, status(정상|특이), memo, photo_url

새 Storage 버킷 care-manual-3d          ← 호점별 glTF 모형 파일
  customers.care_manual.space_model_url
```

상태 색은 저장하지 않고 **빈도 × 마지막 점검일로 매번 계산**합니다. 그래야 데이터가 꼬이지 않습니다.

## 6. 단계별 일정 (총 7~8주, 3주 차에 고객에게 첫 공개 가능)

| 단계 | 기간 | 하는 일 | 끝나면 보이는 것 | 담당 |
|---|---|---|---|---|
| **0. 준비** | 1주 | 3개 호점 도면·건축물대장 수집, 품목 리스트 정리(기존 편집기), 카메라 구매·촬영 연습, 촬영 일정 잡기 | 호점별 구역 목록 확정 | 대표님 + 나 |
| **1. 360 촬영·업로드** | 1주 | 호점별 구역당 1~3지점 촬영, 관리자 편집기에 "360 사진" 업로드 칸 추가 (자동 리사이즈) | 관리자에서 360 사진 돌려보기 | 나 + 현장 |
| **2. 표시·코멘트·링크** | 1~2주 | 사진 위 점·영역 찍기(관리자), 코멘트 입력, 품목 연결, 고객 화면 "공간 보기" 탭 + 품목 자동 스크롤 | **고객에게 첫 공개 가능** (3D 없이도 완결) | 나 |

### 2026-11-09 주기 필터 + 점검 체크 이동 결정
- 뷰어(고객·직원 포털, 관리자 미리보기)에 **주기 필터** 칩 추가: 전체 · 매회 · 주 1회 · 격주 · 월 1회 · 주기 없음. 전체 구역 기준 품목 수 표시, 맞는 품목 없는 묶음은 숨김, 품목으로 이동(표시→품목)할 때는 필터 자동 해제.
